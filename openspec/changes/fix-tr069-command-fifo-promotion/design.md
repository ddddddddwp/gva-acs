## Context

RPC 命令以 MySQL 状态为事实来源，Redis 只保存设备唤醒令牌。当前首条命令提交时会进入 `WAITING_DEVICE`，后续命令进入 `QUEUED`；但首条命令进入 `COMPLETED`、`FAILED` 或 `TIMEOUT` 后，没有生产路径负责提升下一条命令。Redis 消费端只接受 `WAITING_DEVICE` 队首，因此孤立的 `QUEUED` 永远不会执行，服务重启也无法自行恢复。

本次修复不改变状态枚举、数据库结构、管理 API 或前端，只补齐既有 FIFO 生命周期。

## Goals / Non-Goals

**Goals:**

- 任意命令进入终态后，自动提升同设备最早的 `QUEUED` 命令。
- 提升过程在数据库事务内完成，并设置新的设备等待起点和截止时间。
- 数据库提交成功后写入 Redis 唤醒令牌并触发现有 Connection Request 流程。
- 服务启动时恢复孤立 `QUEUED` 队首，并重新唤醒已有 `WAITING_DEVICE` 队首。
- 并发终态、重复恢复和 Redis 失败场景保持幂等且可诊断。

**Non-Goals:**

- 不新增队列状态、API、前端页面或数据库字段。
- 不改变同设备严格 FIFO，也不允许后续命令越过 `SENT`、`BUILDING` 或 `WAITING_TRANSFER`。
- 不把 Redis 提升为命令状态事实来源。

## Decisions

### 独立的队列推进服务

新增服务层队列推进器，由所有终态入口和启动恢复共同调用。推进器在事务中锁定设备行，先检查设备是否存在任何非终态、非 `QUEUED` 的活动命令；只有不存在活动头命令时，才按 `created_at, command_id` 选择最早的 `QUEUED`。

选择设备行锁而不是仅锁候选命令，是为了让“检查活动头”和“选择下一条”具有同一设备粒度的串行化边界，避免并发完成或并发恢复同时提升两条命令。

### 数据库状态先于 Redis 唤醒

推进器在同一事务中执行条件更新 `QUEUED -> WAITING_DEVICE`、设置 `waiting_at` 与 `phase_deadline_at`，并追加状态事件。事务提交后才写 Redis 唤醒令牌。

Redis 入队失败不回滚已经提交的数据库状态，因为数据库是事实来源；推进器追加失败事件，后续启动恢复或下一次扫描可再次入队。

### 终态后推进与启动恢复共用同一逻辑

所有进入 `COMPLETED`、`FAILED`、`TIMEOUT` 的生产入口在终态事务提交后调用推进器。服务启动时扫描具有非终态命令的设备：孤立 `QUEUED` 使用相同推进逻辑，已有 `WAITING_DEVICE` 直接补写唤醒令牌。重复调用通过状态条件和设备锁保持幂等。

### 运行数据只清理重复项

设备 `8CE468-SNB1234567892` 的两条重复 `GetRPCMethods` 中删除较新的 `QUEUED` 命令及其事件，保留较早的一条。修复后的启动恢复负责将保留命令推进并执行。

## Risks / Trade-offs

- [Redis 在数据库提交后失败] → 保留 `WAITING_DEVICE` 和失败事件，启动恢复重新入队，不伪造终态。
- [多个终态入口遗漏接线] → 集中搜索所有终态转换调用，并为成功、失败、超时及启动恢复增加回归测试。
- [并发推进两条命令] → 设备行事务锁、活动头检查和条件状态更新共同保证每台设备最多一个活动头。
- [启动扫描设备数量增长] → 仅扫描存在非终态命令的设备 ID，并逐设备短事务处理；当前不引入周期全表扫描。

## Migration Plan

1. 运行单元测试验证现有实现无法推进 FIFO。
2. 部署推进器及所有终态入口接线。
3. 删除目标设备较新的重复 `GetRPCMethods`。
4. 重启 GVA，启动恢复自动推进保留命令。
5. 验证命令时间线、Redis 唤醒和后续 RPC 执行。

回滚代码不会修改数据库结构；已经推进到 `WAITING_DEVICE` 的命令仍符合旧状态机。运行数据删除仅限重复且尚未执行的命令。
