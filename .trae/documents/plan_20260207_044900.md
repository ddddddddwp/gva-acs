以下是修正后的深度集成计划，重点解决了**进程阻塞**和**资源冲突**问题：

### ⚠️ 核心风险规避 (Critical)

1. **避免主线程阻塞 (最严重风险)**：

   * **问题**：TR069 SDK 既然负责“解析和交互”，极大概率包含一个 HTTP Server (监听 7547 或其他端口)。如果在 GVA 的插件 `Register` 阶段直接调用 SDK 的启动方法（如 `Run()`），**会导致 GVA 主进程卡死**，无法启动后续的 API 服务。

   * **修正方案**：必须使用 `Goroutine` 异步启动 SDK 服务，或者将其 Handler 剥离挂载到 Gin 上。

2. **数据库连接统一**：

   * **问题**：如果 SDK 内部自己初始化了数据库连接池，会与 GVA 的 GORM 连接池冲突，导致资源浪费或事务失效。

   * **修正方案**：**依赖注入**。必须重构 SDK 的初始化逻辑，使其接受 GVA 的 `global.GVA_DB` 实例，而不是自己连库。

3. **日志与配置统一**：

   * **问题**：SDK 可能有自己的日志库和配置文件读取方式，导致日志散落在不同文件，配置难以统一管理。

   * **修正方案**：接管 SDK 的日志输出接口，重定向到 GVA 的 `Zap` 日志；将 SDK 配置项合并到 GVA 的 `config.yaml`。

***

### 📅 修正后的详细实施计划

#### 第一阶段：SDK 适配与改造 (关键)

1. **代码迁入**：

   * 将 SDK 源码放入 `server/plugin/tr069/lib`。
2. **非阻塞启动改造**：

   * 检查 SDK 的入口方法。如果它是阻塞的（如 `http.ListenAndServe`），在 GVA 插件中调用时必须包装：

     ```go
     // server/plugin/tr069/initialize/server.go
     go func() {
         if err := sdk.Start(); err != nil {
             global.GVA_LOG.Error("TR069 SDK启动失败", zap.Error(err))
         }
     }()
     ```
3. **数据库与上下文注入**：

   * 修改 SDK 的初始化函数，增加参数：`func InitSDK(db *gorm.DB, logger *zap.Logger)`。

   * 确保 SDK 内部的所有数据库操作都使用传入的 `db`。

#### 第二阶段：插件层实现

1. **定义插件结构 (GVA Plugin V2)**：

   * `server/plugin/tr069/plugin.go`

   * 实现 `Register` 接口：在此处调用 SDK 的**异步启动**逻辑，并注册必要的 GVA 内部路由。
2. **配置映射**：

   * 在 `server/plugin/tr069/config` 中定义配置结构体（如监听端口、认证信息）。

   * 确保这些配置能从 GVA 的 `config.yaml` 中读取。

#### 第三阶段：业务桥接

1. **双向通信实现**：

   * **上行 (Device -> ACS)**: SDK 解析数据后，不要直接写库（如果逻辑复杂），建议通过 `Callback` 或 `Channel` 通知 GVA 的 Service 层，由 GVA 统一处理业务逻辑（如设备上线提醒）。

   * **下行 (ACS -> Device)**: 在插件的 `Service` 层封装 SDK 的指令发送接口，暴露给 GVA 的 API 使用。

