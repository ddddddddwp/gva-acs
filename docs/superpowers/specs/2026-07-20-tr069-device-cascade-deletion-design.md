# TR-069 设备级联删除设计

## 背景

设备列表当前通过 `DELETE /tr069/device/:deviceId` 删除设备。现有实现只硬删除告警、参数树、Connection Profile 和设备主记录，会遗留 RPC 命令及其事件/XML、设备能力、FAP 服务、日志任务、日志事件、日志文件元数据和 MinIO 对象。

本次变更将“删除设备”定义为设备域数据的永久清除操作。删除完成后不保留设备日志文件、TR-069 业务记录或回收站；GVA 系统操作审计日志仍保留，用于记录删除人、删除时间和执行结果。

## 目标

- 从设备列表删除设备时，永久删除该设备的参数树、RPC 记录、告警、日志文件及其他 TR-069 关联数据。
- 删除 MinIO 中该设备的正式日志对象和正在上传的临时对象。
- 删除期间拒绝该设备的新 RPC、ACS 会话和文件上传，并终止现有运行任务。
- 删除过程可重试，不能因 MinIO 或数据库局部失败产生不可追踪的孤儿数据。
- 删除完成后允许同一设备通过新的 `Inform` 自动注册，形成一套全新的设备数据。
- 不影响其他设备的数据、队列、上传任务和对象。

## 非目标

- 不建立设备黑名单。
- 不提供软删除、回收站或历史恢复。
- 不删除 GVA 系统操作审计日志和通用服务日志。
- 不撤销设备已经接收并执行的 CWMP RPC。强制终止只停止 GVA 侧后续调度、等待和结果接收；协议上已经送达 CPE 的操作无法回滚。
- 不引入数据库和 MinIO 之间的分布式事务。

## 方案选择

### 方案 A：在 API Handler 中直接扩展删除语句

实现量最小，但 API 层会同时承担数据库、Redis、运行任务和对象存储编排，难以测试，也无法清晰处理部分失败和幂等重试。

### 方案 B：独立 DeviceDeletionService 编排删除（采用）

API 只负责参数解析、权限检查和响应；独立服务负责设备封锁、运行态终止、MinIO 清理和数据库事务。该方案与现有 `ArtifactStore` 抽象兼容，便于单元测试，也能在对象存储失败后安全重试。

### 方案 C：数据库外键级联并异步清理 MinIO

数据库侧最简洁，也适合大规模异步回收，但 MinIO 对象会在删除接口成功后继续存在一段时间，不符合本次“立即永久删除”的要求。当前 TR-069 表也没有外键约束，直接改造影响面较大。

## 总体架构

保留现有管理接口：

```http
DELETE /tr069/device/:deviceId
```

新增设备删除编排服务：

```text
DeviceApi.DeleteDevice
        │
        ▼
DeviceDeletionService.Delete
        ├── DeviceDeletionGuard：标记并检查删除状态
        ├── CommandRuntimeCleaner：停止 RPC 调度并清理 Redis 状态
        ├── UploadRuntimeRegistry：拒绝和取消设备上传
        ├── ArtifactStore：永久删除 MinIO 对象
        └── GORM Transaction：硬删除全部关联记录和设备
```

`DeviceDeletionService` 是唯一允许执行设备级联删除的入口。前端不得依次调用多个删除接口，以免浏览器中断、权限差异或单次请求失败造成局部删除。

## 删除状态与并发控制

在 `tr069_devices` 增加可空字段 `deleting_at`。删除服务首先使用条件更新将它设置为当前时间：

```sql
UPDATE tr069_devices
SET deleting_at = NOW()
WHERE id = ? AND deleting_at IS NULL;
```

状态规则：

- 更新一行：当前请求取得删除权并继续执行。
- 已经存在且 `deleting_at` 非空：视为同一删除操作的重试，继续清理。
- 设备不存在：返回设备不存在，不创建删除记录。
- 删除失败：保留设备及 `deleting_at`，使设备保持封锁状态并允许用户重试。
- 删除完成：硬删除设备行。设备之后发送 `Inform` 时，因为旧记录已经不存在，可以按现有注册流程重新创建。

以下入口必须检查设备未处于删除状态：

- 管理端新建 RPC 命令。
- ACS 接收已有设备的 Inform、RPC Response 和 TransferComplete。
- `/acs/log`、`/acs/pm`、`/acs/mr` 文件上传认证完成后的设备校验。
- 日志文件下载接口。

删除中的管理请求返回冲突错误；设备侧 ACS/文件请求按现有未注册或不可用响应规范拒绝。ACS 注册逻辑发现同一标识的旧设备正在删除时不得创建第二条设备记录。

## 运行态终止

删除取得设备封锁状态后执行运行态清理：

1. 阻止该设备创建新的 RPC 和上传上下文。
2. 从 Redis 删除该设备的 FIFO 队列、唤醒令牌和 Connection Request 调度状态。
3. 取消该设备当前由 GVA 持有的 RPC 等待上下文；迟到的响应不再推进命令状态。
4. 通过上传运行注册表取消该设备当前上传请求的 Context，并调用当前 `ArtifactWriter.Abort()`。
5. 等待取消动作返回后再开始对象删除，避免上传协程重新写入刚删除的对象键。

上传运行注册表按 `deviceId` 保存当前上传取消函数。文件入口在开始流式接收前注册，在 Commit、Abort 或请求结束时注销。注册动作必须与删除封锁检查组合，避免“删除已开始但上传刚好完成认证”的竞态。

当前项目按单个 GVA/TR-069 后端实例运行，运行注册表负责本进程取消。数据库 `deleting_at` 是跨请求的事实来源；未来扩展多个 ACS 实例时，可在不改变删除服务接口的情况下增加 Redis Pub/Sub 广播取消事件。

## MinIO 对象清理

删除服务在数据库仍保留完整关联关系时查询该设备的所有 `tr069_artifacts.object_key`。对象清理由 `ArtifactStore.Delete(ctx, key)` 完成，业务层不直接依赖 MinIO SDK。

规则：

- 正式对象、失败对象和 `RECEIVING` 对象都必须清理。
- 已停止的上传先执行 Abort，再删除它记录的对象键。
- 对象不存在视为成功，保证重试幂等。
- 对象删除采用有限并发，避免一次删除大量日志压垮 MinIO；第一阶段固定最多 4 个并发删除请求。
- 任意非“对象不存在”错误都会停止数据库删除并返回错误。
- 已经成功删除的对象不恢复；重试时再次删除这些对象仍然成功。
- 设备处于 `DELETING` 时禁止下载日志，避免数据库尚存但对象已部分删除时向用户返回不一致内容。

MinIO 和 MySQL 无法共享事务，因此采用“对象先删、数据库后删”的可重试顺序。这样即使部分对象删除失败，数据库中仍保留剩余对象键，后续重试仍有完整的清理依据，不会产生无法定位的 MinIO 孤儿对象。

## 数据库级联清理

MinIO 全部清理成功后，在一个 GORM 数据库事务中执行硬删除。当前 TR-069 表没有外键，服务必须显式维护顺序和条件。

删除顺序：

1. 根据设备查询 `command_id`、`task_id` 和 `file_id` 集合。
2. 删除 `tr069_transfer_events`，条件为关联 `task_id` 或 `file_id`。
3. 删除 `tr069_artifacts`。
4. 删除 `tr069_transfer_tasks`。
5. 删除 `tr069_command_xmls`。
6. 删除 `tr069_command_events`。
7. 删除 `tr069_commands`。
8. 删除 `tr069_alarms` 和 `support_tr069_alarms`。
9. 删除 `tr069_datamodel_values`。
10. 删除 `tr069_device_rpc_methods`。
11. 删除 `tr069_fap_services`。
12. 删除 `tr069_connection_request_profiles`。
13. 硬删除 `tr069_devices`。

所有直接关联表都使用 `device_id` 过滤；事件表使用删除前查询到的父级标识过滤。禁止使用不带设备范围的全表删除。事务中任意 SQL 失败时全部回滚，设备继续保持 `DELETING`，再次调用接口可重试。

`tr069_migration_markers` 是插件级迁移状态，不属于设备数据，不参与删除。

## API 与前端行为

现有删除权限和路由保持不变，不新增管理 API。

设备列表删除确认文案调整为：

> 删除设备将永久删除该设备的参数树、RPC 记录、告警和全部日志文件，且无法恢复。确定继续吗？

交互规则：

- 用户确认后，删除按钮进入加载状态，禁止重复点击。
- 删除服务完成全部 MinIO 和数据库清理后才返回成功。
- 成功后刷新设备列表、参数和日志相关缓存。
- 失败时显示后端返回的失败阶段，设备仍保留但不可操作；用户可再次点击删除重试。
- 删除中的设备如果仍出现在列表中，操作列只保留“重试删除”，不允许下发 RPC、查看参数或下载日志。

## 错误处理与日志

删除日志只记录设备数据库 ID、序列号摘要、阶段、记录数量、对象数量、耗时和错误，不记录 Connection Request 密码、文件内容或完整 XML。

错误阶段统一为：

- `mark_deleting`：设备不存在或无法取得删除状态。
- `stop_runtime`：RPC、Redis 或上传终止失败。
- `delete_artifacts`：MinIO 对象删除失败。
- `delete_database`：数据库事务失败。

成功日志记录各类删除数量。失败响应不暴露 MinIO 密钥、数据库语句或内部对象路径，只返回可理解的阶段说明；详细原因写入 GVA 后端日志。

## 测试设计

### 服务单元测试

- 删除设备时清除全部直接关联记录。
- 删除命令前清除其事件和 XML。
- 删除日志任务前清除日志事件、制品记录和 MinIO 对象。
- 仅删除目标设备，另一台设备的同类记录和对象保持不变。
- 正在上传的文件被取消并执行 Abort。
- 排队、等待和执行中的 RPC 运行态被清除。
- 删除封锁建立后拒绝新的 RPC、ACS 会话、文件上传和日志下载。
- MinIO 返回对象不存在时继续完成删除。
- MinIO 删除失败时不删除数据库记录，设备保持 `DELETING`。
- 部分对象已删除后重试能够幂等完成。
- 数据库事务失败时关联记录全部回滚。
- 删除完成后同一序列号的 Inform 可以重新注册。

### API 测试

- 无权限用户无法删除设备。
- 不存在的设备返回明确错误。
- 删除成功只在全部清理完成后返回。
- 删除失败响应包含安全的阶段说明。

### 前端测试

- 二次确认明确提示参数、RPC、告警和日志文件永久删除。
- 删除期间按钮禁用并显示加载状态。
- 成功后刷新列表，失败后允许重试。

### 集成验证

准备两台设备及各自的参数、RPC、告警、日志任务和 MinIO 对象。删除其中一台后验证目标设备全部数据和对象消失，另一台所有数据保持不变；随后让已删除设备发送 Inform，验证它可以重新注册且不会恢复旧数据。

## 完成标准

- 删除设备后，目标设备在所有设备域 TR-069 表中的关联记录均为零。
- MinIO 中不存在目标设备 `tr069_artifacts` 曾引用的任何对象。
- Redis 中不存在目标设备的 RPC 队列和唤醒状态。
- 删除过程中无法为目标设备创建新业务数据。
- 其他设备的数据和运行状态不受影响。
- 同一设备后续 Inform 可以正常创建新设备记录。
- 相关单元测试、API 测试和现有 TR-069 回归测试全部通过。
